# Aware Implementation Plan

## Overview

**Aware** is an installable context-first workflow for AI coding agents.

It is designed to work across different repositories and systems by teaching the agent how to gather enough relevant context before investigating, planning, editing, or reviewing code.

Aware is implemented as an AI skill repository, similar in structure to projects such as Caveman.

The main behavior lives in a `SKILL.md` file. Supporting files provide installation, agent compatibility, commands, tests, and documentation.

Aware is not initially intended to be:

- A repository indexing service
- A vector database
- A hosted application
- A code search engine
- A standalone autonomous coding agent
- A project-specific VS Code extension

The first version should remain lightweight and portable.

---

## Product Goal

Aware should prevent AI coding agents from immediately guessing, editing unrelated files, or loading an entire repository without direction.

The workflow should guide the agent through the following sequence:

```text
Understand request
Find project instructions
Locate likely entry points
Inspect relevant files
Trace relationships
Separate facts from assumptions
Summarize working context
Plan the smallest safe change
Implement
Verify
Report
```

The primary question Aware should answer is:

> What does the agent need to understand before working on this task?

---

## Core Principles

### Context before implementation

The agent should gather relevant evidence before proposing or making changes.

### Relevant context only

The agent should not scan the entire repository by default.

It should begin with the files, symbols, errors, routes, commands, tests, and components directly related to the task.

### Evidence over assumptions

The agent should distinguish between:

- Verified information
- Inferences
- Unknowns
- Risks

### Smallest safe change

The agent should prefer the smallest coherent implementation that satisfies the task while preserving existing conventions.

### Portable workflow

The skill should work with:

- Codex
- Claude Code
- Gemini CLI
- Cursor
- Windsurf
- Cline
- GitHub Copilot
- Other agents that support skill or instruction files

## Initial `SKILL.md` Draft

```markdown
---
name: aware
description: >
  Context-first workflow for AI coding agents. Use when working on an
  unfamiliar project, investigating bugs, implementing features, planning
  changes, reviewing code, or when the user asks the agent to understand
  the system before making changes.
---

Use a context-first workflow before making substantial changes.

## Goal

Understand enough of the system to make a grounded change without reading
the entire repository or guessing about unseen behavior.

## Persistence

Apply this workflow throughout the task.

Do not abandon context gathering after the first response.

Continue validating assumptions when new evidence appears.

## Core Workflow

1. Understand the requested outcome.
2. Read applicable project instructions.
3. Identify likely entry points.
4. Inspect directly related files.
5. Trace dependencies, callers, routes, tests, and configuration.
6. Separate verified facts from assumptions.
7. Summarize the working context.
8. Plan the smallest safe change.
9. Implement only after sufficient context exists.
10. Run relevant verification.
11. Report findings, changes, and remaining uncertainty.

## Project Instructions

Before substantial work, look for:

- `AGENTS.md`
- `CLAUDE.md`
- `GEMINI.md`
- `README.md`
- `CONTRIBUTING.md`
- architecture documentation
- project-local AI instruction files
- documentation near the files being changed

Follow the most specific applicable instruction.

Do not assume root-level instructions are the only instructions.

## Context Discovery

Start with:

- files named by the user
- current file
- changed files
- exact error messages
- symbols mentioned in the task
- routes or commands involved
- related tests
- direct imports
- direct callers
- nearby configuration

Expand only when evidence requires it.

Do not scan the entire repository by default.

## Working Context

Before implementation, establish:

- requested outcome
- current behavior
- relevant components
- relevant files
- affected data flow
- existing conventions
- likely change area
- constraints
- unresolved questions
- intended verification

Keep the summary compact.

Do not create a repository encyclopedia.

## Evidence Labels

Use labels when they improve clarity:

- `[Verified]` Supported directly by inspected code, tests, logs, or docs.
- `[Inference]` Strongly suggested by available evidence.
- `[Unknown]` Not established yet.
- `[Risk]` Could cause regression, data loss, security issues, or compatibility issues.

Never present an inference as a verified codebase fact.

## Investigation Rules

- Read exact errors before proposing fixes.
- Find where the relevant behavior begins.
- Trace the behavior across boundaries when necessary.
- Inspect existing tests before designing a fix.
- Compare working and failing paths when both exist.
- Check configuration and environment differences.
- Stop and reassess when evidence contradicts the current theory.
- Do not fabricate files, symbols, dependencies, or APIs.

## Planning Rules

A plan should identify:

- files likely to change
- files that must be inspected
- expected behavior
- implementation sequence
- risks
- verification steps

Plans should be proportional to the task.

Do not produce a large architecture plan for a one-line fix.

## Implementation Rules

- Prefer the smallest coherent change.
- Do not modify unrelated code.
- Preserve project conventions.
- Reuse existing abstractions when appropriate.
- Do not introduce new dependencies without justification.
- Keep public behavior backward-compatible unless the task requires otherwise.
- Update tests when behavior changes.
- Do not hide uncertainty behind confident language.

## Verification Rules

Use the narrowest meaningful verification first:

1. Targeted tests
2. Type checking
3. Linting
4. Build
5. Broader test suite

Do not claim verification succeeded unless the command was actually run and passed.

When verification cannot be run, say why.

## Completion Format

Report:

- what was understood
- what changed
- why it changed
- files affected
- verification performed
- remaining risks or unknowns

## Boundaries

Do not:

- read every file without a reason
- produce large context dumps
- repeat the same findings
- make unrelated cleanup changes
- assume undocumented behavior
- claim tests passed without running them
- invent project commands
- expose secrets
- modify generated files unless required
```

## Skill Behavior Design

### Trigger conditions

Aware should activate when the user asks to:

- Investigate a bug
- Understand a system
- Add a feature
- Modify existing behavior
- Review a change
- Write an implementation plan
- Trace a workflow
- Explain unfamiliar code
- Prepare a technical ticket
- Work on an unfamiliar repository

Example trigger phrases:

```text
understand this project
investigate this issue
trace this workflow
find where this behavior happens
create an implementation plan
fix this bug
review this feature
work context-first
use aware
```

The skill should not activate for:

- Simple factual programming questions
- Isolated code snippets with complete context
- Basic syntax questions
- General writing tasks
- Non-technical requests

---

## Context Workflow

### Step 1: Understand the request

The agent should identify:

- Desired result
- Current problem
- Scope
- Constraints
- Mentioned technologies
- Mentioned files
- Exact error messages

### Step 2: Find project instructions

The agent should inspect instruction files before substantial work.

Priority should generally be:

1. Instructions closest to the target files
2. Repository-specific instructions
3. Root-level instructions
4. User instructions
5. General skill defaults

### Step 3: Locate entry points

Possible entry points include:

- Route
- Controller
- Handler
- Component
- Screen
- Command
- Job
- Service
- Model
- Event listener
- Configuration
- Test
- Error stack trace

### Step 4: Trace relationships

Depending on the task, inspect:

- Imports
- Callers
- Callees
- Routes
- Data models
- Database access
- API clients
- State management
- Background jobs
- Tests
- Environment configuration
- Deployment configuration

### Step 5: Establish working context

The agent should create a small internal or visible summary.

Example:

```markdown
## Working Context

[Verified] The mobile client connects to `/cable`.

[Verified] The production endpoint is routed through CloudFront.

[Verified] Android succeeds while iOS receives HTTP 403.

[Verified] A direct ngrok connection succeeds.

[Inference] The failure is likely in the CloudFront or WAF handshake path rather
than the Rails Action Cable implementation.

[Unknown] The exact CloudFront rejection reason has not yet been confirmed.
```

### Step 6: Plan

The plan should be based on inspected evidence.

It should avoid speculative file lists.

### Step 7: Implement

The agent should edit only when it has enough context to explain why the change belongs in that location.

### Step 8: Verify

The verification should match the change.

### Step 9: Report

The final report should distinguish:

- Completed work
- Verified behavior
- Remaining uncertainty
- Recommended next action

## Optional Sub-Skills

The main `aware` skill should be enough for the MVP.

Sub-skills can be added later.

### `aware-scan`

Purpose:

- Inspect project structure
- Identify frameworks
- Find instructions
- Find entry points
- Produce a compact project map

Possible command:

```text
/aware-scan
```

Output:

```markdown
## Project Map

- Application type
- Main framework
- Important directories
- Entry points
- Test locations
- Configuration
- Existing instructions
```

### `aware-plan`

Purpose:

- Create an implementation plan based on inspected repository evidence

Possible command:

```text
/aware-plan <task>
```

Rules:

- Inspect before planning
- Name only verified files
- Mark likely files separately
- Include testing and risks
- Keep scope proportional

### `aware-update`

Purpose:

- Update project documentation after implementation

Possible command:

```text
/aware-update
```

It should update files such as:

- `AGENTS.md`
- `README.md`
- Architecture documentation
- Feature inventory
- Change notes
- Project-specific context files

It must not update documentation automatically without reviewing the actual changes.

- Print clear results

## Project Initialization

An optional initializer can create repository-local instructions.

Command:

```bash
npx aware --with-init
```

Possible output:

```text
.aware/
└── config.json

AGENTS.md
```

Example config:

```json
{
  "enabled": true,
  "mode": "balanced",
  "showWorkingContext": true,
  "useEvidenceLabels": true,
  "updateProjectDocs": false
}
```

Possible modes:

### `light`

- Read instructions
- Inspect directly related files
- Avoid unnecessary context dumps

### `balanced`

- Full context-first workflow
- Evidence labels
- Working context summary
- Plan before substantial changes

### `strict`

- Require explicit verified context
- Require plan
- Require verification
- Report all unknowns and risks

The MVP should use one default mode before introducing configurable modes.

## Testing Strategy

### Structural tests

Validate:

- `SKILL.md` exists
- Frontmatter is valid
- Skill name is correct
- Description exists
- Required sections exist
- No broken internal links
- Commands reference valid skills

### Behavior tests

Use prompt fixtures.

Example fixture:

```json
{
  "prompt": "Fix the login timeout bug",
  "expectedBehaviors": [
    "reads project instructions",
    "locates authentication entry point",
    "checks related tests",
    "does not immediately edit unrelated files",
    "labels assumptions"
  ]
}
```

### Negative behavior tests

Validate that the agent does not:

- Claim unseen code behavior
- Invent files
- Scan everything without reason
- Claim tests passed without execution
- Produce a plan based only on filenames
- Perform unrelated refactoring

### Scenario fixtures

Create examples for:

```text
tests/fixtures/
├── bug-investigation/
├── feature-request/
├── unfamiliar-repository/
├── code-review/
├── implementation-plan/
└── documentation-update/
```

### Evaluation questions

For each scenario:

- Did the agent inspect applicable instructions?
- Did it find the correct entry point?
- Did it inspect related files?
- Did it distinguish facts from inferences?
- Did it avoid unrelated files?
- Was the plan based on evidence?
- Was verification appropriate?
- Was the final report accurate?

## Final Product Direction

Aware should be positioned as:

> A portable context-first workflow for AI coding agents.

The value is not that it gives the agent more information.

The value is that it teaches the agent to find the right information before acting.

```text
Caveman controls how the agent speaks.
Aware controls how the agent understands the work.
```
